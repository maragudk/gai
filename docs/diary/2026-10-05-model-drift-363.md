# Diary: Triage the eight-model conformance drift in issue #363

The daily `Conformance` workflow filed issue #363 and has failed every day since at least 2026-10-01. The 2026-10-05 run (37281293481) reports drift in all three client packages at once: eight live model IDs that `TestModelConformance` neither exports nor ignores. This diary triages them by the written curation policy and lands the fix.

## Step 1: Diagnose the drift and assign dispositions by precedent

**Author:** main

### Prompt Context

**Verbatim prompt:** "See issue 363"
**Interpretation:** Resolve GitHub issue #363, the auto-filed `model-drift` issue, the same way earlier drift issues (#355 and others) were resolved: triage, fix, and open a PR.
**Inferred intent:** Get the daily `Conformance` workflow green again by applying the existing curation policy, not by re-deciding policy.

### What I did

Read issue #363 with `gh issue view 363 --json ...` (the plain `--comments` form printed nothing again, as noted in the 2026-09-08 diary). The issue body only links a run, so I pulled the newest failing run with `gh run view 37281293481 --log-failed`. The `every listed model ID is exported or ignored` subtest fails in each client:

- `/clients/anthropic`: `claude-opus-5-5, claude-sonnet-5-5`
- `/clients/google`: `gemini-3.8-flash-lite-tts, gemini-3.8-flash-tts`
- `/clients/openai`: `gpt-6-luna, gpt-6-sol, gpt-6.1-sol, gpt-live-1`

I checked the curation policy in `/docs/decisions.md` and the existing constants and ignore lists, then created worktree `model-drift-363` from `origin/main` and started this diary.

Dispositions, all by precedent:

- `claude-opus-5-5`, `claude-sonnet-5-5`: export. They are current-generation point releases of the already-exported `claude-opus-5` and `claude-sonnet-5`, the same shape as `claude-fable-5-1`.
- `gemini-3.8-flash-tts`, `gemini-3.8-flash-lite-tts`: ignore. TTS is a modality variant, and earlier `*-tts` IDs are already on the Google ignore list.
- `gpt-6-luna`, `gpt-6-sol`, `gpt-6.1-sol`: export, following the `gpt-6-astra` and GPT-5.6 Luna/Sol/Terra precedent. The condition is that each one completes a real chat-completions request. If one is Responses-API-only, it goes on the ignore list with a caveat comment instead.
- `gpt-live-1`: ignore by default as a realtime/live surface, next to `gpt-realtime*` and `gpt-live-transcribe`. A live probe settles it: if it unexpectedly works as a plain chat-completions model, the builder reports back rather than exporting it.

### Why

The policy already covers every case here. Re-deciding it per model would be busywork, and it would let the lists drift away from the written rule.

### What worked

The CI log named every drifting ID, so the triage was a lookup against the policy and the existing ignore patterns.

### What didn't work

`gh issue view 363 --comments` printed nothing and gave no error. The `--json` form worked.

### What I learned

Drift had piled up for several days across all three providers before anyone looked at it. The single-issue dedup in the workflow means later drift adds no new signal while #363 stays open.

### What was tricky

Nothing yet. The open question is whether the new GPT-6 IDs work through chat completions, which only a live call can answer.

### What warrants review

The builder's live verification for each exported model, and that ignore entries sit in the correct commented group of each ignore list.

### Future work

Exporting more current models does not by itself age older ones out of the generation window. That is a separate curation pass, out of scope here.

## Step 2: Implement the dispositions, with live probing

**Author:** drift-builder

### Prompt Context

**Verbatim prompt:** "Fix GitHub issue #363 (model conformance drift) in the gai repo ... First re-run `make conformance` to confirm the set is unchanged." Later, after the first hand-back: "Markus has refreshed the OpenAI key, and I copied the updated `.env.test.local` into the worktree root ... Continue from where you stopped and finish all of it in one PR that closes #363."
**Interpretation:** Apply the lead's decided dispositions for the eight drifting IDs, verified live, in one PR.
**Inferred intent:** Get the daily `Conformance` workflow green without re-deciding policy, and keep the `ThinkingLevel` docs honest for the new GPT-6 models.

### What I did

First `make conformance` run confirmed the Anthropic and Google sets exactly (`claude-opus-5-5, claude-sonnet-5-5` and `gemini-3.8-flash-lite-tts, gemini-3.8-flash-tts`). OpenAI could not be confirmed because the key failed. After the key was refreshed, the OpenAI set was exactly `gpt-6-luna, gpt-6-sol, gpt-6.1-sol, gpt-live-1`.

Edits:

- `/clients/anthropic/chat_complete.go`: added `ChatCompleteModelClaudeSonnet5_5Latest` and `ChatCompleteModelClaudeOpus5_5Latest` from the SDK constants, after the Claude 5 constants, and added both to `exportedModels` in `/clients/anthropic/model_conformance_test.go`. I also switched `ChatCompleteModelClaudeFable5_1Latest` from the `"claude-fable-5-1"` literal to `anthropic.ModelClaudeFable5_1` (the lead approved this), which removes the stale "SDK does not ship it yet" comment.
- `/clients/google/model_conformance_test.go`: ignored `gemini-3.8-flash-tts` and `gemini-3.8-flash-lite-tts` in the TTS group.
- `/clients/openai/chat_complete.go`: added `ChatCompleteModelGPT6Luna`, `ChatCompleteModelGPT6Sol` and `ChatCompleteModelGPT6_1Sol` after `ChatCompleteModelGPT6Astra`, exported in `/clients/openai/model_conformance_test.go`. Ignored `gpt-live-1` in the "Audio, realtime, ..." group.
- Updated the `ThinkingLevel` doc comments and added 18 rows to the reasoning-effort matrix in `/clients/openai/chat_complete_test.go`.
- `go.mod`/`go.sum`: `anthropic-sdk-go` v1.71.0 to v1.77.0 and `openai-go/v3` v3.56.0 to v3.70.0 (see below for why not the newest).

Live probe (throwaway test using the package's `newChatCompleter` helper, deleted before committing), each model through `ChatCompleter.ChatComplete` with the "17 sheep" prompt at the default level and every `ThinkingLevel`:

- `gpt-6-luna`: completes. Accepts none/low/medium/high/xhigh; `minimal` is a 400.
- `gpt-6-sol`: completes. Same accepted range as luna.
- `gpt-6.1-sol`: completes. Accepts low/medium/high/xhigh; `none` and `minimal` are both 400 (like `gpt-6-astra`).
- `gpt-live-1`: 404 Not Found at every level, so it is not available on chat completions. Ignored.

I then ran the new matrix rows four times with `-count=4 -shuffle on`; all new rows passed every time. The only failure in that run was the pre-existing `gpt-6-astra + medium` row (`chat_complete_test.go:574: thoughts tokens should be populated`), once in four runs. That is a flaky `wantThoughtTokens` assertion from an earlier change, not touched here.

### Why

The lead's curation policy already decided every disposition. The only open question was whether the GPT-6 trio works through chat completions, and the probe answers that: yes.

### What worked

The SDK constants exist for all five exported models, so no string literals were needed. Probing at every level before writing docs caught a real difference between `gpt-6.1-sol` and its siblings (it rejects `none`). Copying the shape of the `gpt-6-astra` matrix block made the new rows quick to write.

### What didn't work

1. The first `make conformance` failed the whole OpenAI package with the stale key. Verbatim, for each subtest: `GET "https://api.openai.com/v1/models": 401 Unauthorized { "message": "Incorrect API key provided: sk-proj-****...3S0A. ...", "type": "invalid_request_error", "param": null, "code": "invalid_api_key" }`.
2. To check the key I tried to source `.env.test.local` and `curl` the models endpoint while printing the key's prefix and suffix. The auto-mode classifier denied it: `Permission for this action was denied by the Claude Code auto mode classifier. Reason: [Credential Materialization].` That was a mistake on my side: the command printed pieces of the key. I did not retry it in any other form. A following `GAI_MODEL_CONFORMANCE=1 go test ...` for anthropic and google was denied with the same reason, so I stopped and reported to the lead, who supplied a refreshed key.
3. Bumping both SDKs to the newest versions broke the lint gate: `golangci-lint run` reported 4 `SA1019` issues. With `anthropic-sdk-go` v1.78.0: `ModelClaudeSonnet4_5 is deprecated: Will reach end-of-life on November 30, 2026. Please migrate to claude-sonnet-5-5.` With `openai-go/v3` v3.71.1: `ChatModelGPT5`, `ChatModelGPT5Mini` and `ChatModelGPT5Nano` are deprecated with `Announced shutdown date: 2026-12-11`. Aging those models out is explicitly out of scope, so I stepped back instead of adding `nolint` markers.

4. The full `go test -count=1 -shuffle on ./...` run with keys failed only in `/clients/google`, with a panic from the Vertex AI service-account tests: `panic: project/location or API key must be set when using Vertex AI backend. ClientConfig: &genai.ClientConfig{APIKey:"", Backend:2, Project:"", Location:"global", Credentials:(*auth.Credentials)(nil) ...`. `.env.test.local` has no `GOOGLE_VERTEX_CREDENTIALS_PATH` (service-account file), so `newVertexAIClientWithCredentials` builds an empty client, and the Vertex embedder test fails the same way. This is an environment gap, not a regression. With `-skip '/Vertex|service_account'` the rest of the package passes, and the Google conformance test passes.

### What I learned

The newest SDK versions start marking still-live models as deprecated, which trips `staticcheck` on the exported constants. I bisected the versions: `anthropic-sdk-go` v1.76.0 has `ModelClaudeSonnet5_5`, `ModelClaudeOpus5_5` and `ModelClaudeFable5_1` (v1.74.0 has one of the three; v1.75.0 not checked), and v1.77.0 is the newest without the new deprecation. `openai-go/v3` v3.67.0 is the first with all three GPT-6 constants, and v3.70.0 is the newest before the deprecations (v3.71.0 already trips them). I pinned the newest lint-clean version of each.

Self-review (code-review skill, two rounds of findings) led to these changes: dropped the thought-token assertion on `gpt-6-luna + low` (low effort is not guaranteed to reason, and its siblings returned 0 tokens there); rewrapped an over-long doc line; moved the Google TTS ignore entries after `gemini-3.5-transcribe` to keep version order; added a caveat comment for `gpt-live-1`; and probed `claude-sonnet-5-5` and `claude-opus-5-5` live at default/none/low/high/xhigh/max (all complete and accept every level), then corrected the Anthropic `ThinkingLevelXHigh` doc comments, which still said xhigh was Opus-4.7-only. I did not add Anthropic matrix rows, since the Claude 4.8 and 5 models have none either.

### What was tricky

Sandbox rules refused some compound shell commands that merely contained a module path with `github.com` in a `$(...)`; splitting them or using a script in the scratchpad worked. The bisect script was also fragile: when a version lacks the constants the code does not compile, so the lint count is only meaningful where the constant count is complete.

### What warrants review

- The two SDK pins, and that the transitive bumps in `go.mod` (`golang.org/x/crypto`, `x/net`, `x/text`, new indirect `github.com/coder/websocket`) come only from the SDKs' requirements via `go mod tidy`.
- The `ThinkingLevel` doc comment edits in `/clients/openai/chat_complete.go`, especially that `gpt-6.1-sol` rejects `none`.
- The new matrix rows: `low` rows for `gpt-6-sol` and `gpt-6.1-sol` make no thought-token assertion because the probe returned 0 tokens there.

### Future work

The deprecations that stop us from taking the newest SDKs (`gpt-5`, `gpt-5-mini`, `gpt-5-nano` shutting down 2026-12-11; `claude-sonnet-4-5` ending 2026-11-30) need an age-out pass before the next SDK bump. The `gpt-6-astra + medium` thought-token assertion is flaky and could be relaxed.
