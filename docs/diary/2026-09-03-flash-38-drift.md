# Diary: Export `gemini-3.8-flash` and ignore `gemini-flash-latest-high-res-exp` to fix Google model conformance drift

The daily `Conformance` workflow opened issue #353 after Google's live model list grew two IDs that `TestModelConformance` in `/clients/google` neither exports nor ignores. This diary triages them by the written curation policy and lands the fix.

## Step 1: Diagnose the drift and decide by precedent

**Author:** main

### Prompt Context

**Verbatim prompt:** "Fix 353"
**Interpretation:** Resolve GitHub issue #353, the auto-filed `model-drift` issue from the `Conformance` workflow run 33729803101.
**Inferred intent:** Keep the model-constant lists current with minimal ceremony by applying the existing curation policy rather than re-deciding each new model.

### What I did

Read issue #353 with `gh issue view`, then pulled the failing test output from the CI run with `gh run view 33729803101 --log-failed`. The `every listed model ID is exported or ignored` subtest in `/clients/google/model_conformance_test.go` reports: `export or ignore these model IDs: gemini-3.8-flash, gemini-flash-latest-high-res-exp`. The existence check for the already-exported constants passed, so nothing was killed server-side. Compared the two IDs against the exported constants in `/clients/google/chat_complete.go` (which already carry `Gemini3_5Flash`, `Gemini3_6Flash`, `Gemini3_7Flash`) and the `ignoredModels` list (which already carries the `gemini-flash-latest` floating alias). Created worktree `flash-38-drift` from `origin/main`, started this diary, and delegated the change to a builder.

### Why

The policy exports stable, GA, current-generation models that work through the client's implemented API surface, and excludes floating aliases and previews/experiments without a stable counterpart. `gemini-3.8-flash` is the next point release of an already-exported family: export as `ChatCompleteModelGemini3_8Flash`. `gemini-flash-latest-high-res-exp` is both a `-latest` floating alias and an `-exp` experiment: ignore, listed next to the other floating aliases.

### What worked

The failing test's message named the exact IDs, and the pattern of the three preceding Flash point releases plus the existing `gemini-flash-latest` ignore entry made both dispositions a lookup.

### What didn't work

Nothing failed at this stage.

### What I learned

Google is now shipping Flash point releases roughly monthly; each one costs one drift issue and one small PR. That is acceptable, but if it accelerates, a prefix pattern for the Flash family in the export check would be worth considering.

### What was tricky

Nothing technical. The session started on `main` at the repository root rather than in a worktree, so the worktree had to be created explicitly before any work.

### What warrants review

After the builder's change: the new constant sits in version order in the const block and in `exportedModels`; the ignore entry sits under the floating-alias comment; the constant was live-verified through `ChatCompleter` (a plain chat completion, not only `Models.Get`); the Google `TestModelConformance` is green live; `/docs/index.html` and the client README were swept for constant enumerations.

### Future work

None beyond closing #353 when the PR merges.

## Step 2: Land the constant and the ignore entry, blocked on live verification

**Author:** flash-builder

### Prompt Context

**Verbatim prompt:** "Fix GitHub issue #353 (model conformance drift). The daily `Conformance` workflow's `TestModelConformance/every_listed_model_ID_is_exported_or_ignored` in `clients/google` fails with: `export or ignore these model IDs: gemini-3.8-flash, gemini-flash-latest-high-res-exp`. [...] 1. **Export `gemini-3.8-flash`** as `ChatCompleteModelGemini3_8Flash = ChatCompleteModel("gemini-3.8-flash")` in `clients/google/chat_complete.go`, directly after `ChatCompleteModelGemini3_7Flash` [...] 2. **Ignore `gemini-flash-latest-high-res-exp`** by adding it as an exact entry to `ignoredModels` [...] 3. **Live-verify** `gemini-3.8-flash` works through `ChatCompleter` with a real chat completion [...] If it does NOT work, do not export it; add it to the ignore list with the verbatim error in the comment and report back."
**Interpretation:** Apply the two dispositions the lead already decided, prove the new constant works against the live API before exporting it, and confirm the conformance test goes green.
**Inferred intent:** Close #353 with a change that is both mechanically correct and actually true of the provider, rather than a list edit that merely silences the test.

### What I did

Added `ChatCompleteModelGemini3_8Flash = ChatCompleteModel("gemini-3.8-flash")` to the const block in `/clients/google/chat_complete.go`, directly after `ChatCompleteModelGemini3_7Flash`; the existing column alignment already accommodates the shorter name, confirmed by `gofmt -l ./clients/google/` returning nothing. Added the matching `string(google.ChatCompleteModelGemini3_8Flash)` row to `exportedModels` in `/clients/google/model_conformance_test.go` in the same position, and added `"gemini-flash-latest-high-res-exp"` as an exact entry to `ignoredModels`, sorted between `gemini-flash-latest` and `gemini-flash-lite-latest`. Widened that group's comment from "Floating aliases that track the newest model" to "Floating aliases that track the newest model, and experimental variants of those aliases", since the new entry is an `-exp` variant of the alias rather than a plain alias and the old wording no longer covered the group.

Swept `/docs/index.html` and `/clients/google/README.md` for enumerations of Google model constants. Neither lists any: the README is a twelve-line stub with no occurrence of "model" at all, and `docs/index.html` mentions `clients/google` only as a GitHub link on line 355. No documentation change is needed, confirming the lead's grep.

Then tried to live-verify, and could not. The package's `newClient(t)` helper calls `env.Load("../../.env.test.local")` and reads `GOOGLE_KEY`; the worktree has no `.env.test.local` (it is gitignored as `/.env.*.local` and therefore does not come along when a worktree is created), and no `GOOGLE_KEY` is set in my environment. Every attempt panics inside `google.NewClient` at `/clients/google/client.go:85`.

### Why

Both dispositions follow the curation policy verbatim. `gemini-3.8-flash` is the next point release of the already-exported Flash line (3.5, 3.6, 3.7 are all constants), so it belongs in the const block. `gemini-flash-latest-high-res-exp` is simultaneously a `-latest` floating alias and an `-exp` experiment, and the policy excludes both categories, so it belongs in the ignore list; the exact-match form matches the precedent set by the three alias entries already there, and a `gemini-flash-latest*` prefix would additionally swallow any future `gemini-flash-latest-<something>` without anyone noticing.

The live verification is not ceremony. The policy excludes models that "cannot work through the client's implemented API surface", and the ignore list already carries two models — `gemini-omni-1.1-flash` and `gemini-omni-flash-preview` — that advertise `generateContent` in the list response and still answer every call with `400 INVALID_ARGUMENT, This model only supports Interactions API.`. `Models.Get` succeeds for those too. So a get-by-ID probe cannot distinguish an exportable model from an alive-but-unusable one; only a real chat completion can.

### What worked

The mechanical part was a lookup, exactly as the lead predicted. `gofmt` needed no realignment, `golangci-lint run` reports `0 issues.`, and `go build ./...` and `go vet ./clients/google/` are both clean.

The documentation sweep was quick to make non-vacuous: rather than trusting a grep that returned nothing, I checked that the files have content at all (`wc -l` gives 12 and 470 lines) and grepped for the client paths to confirm the pattern would have matched something if a list existed.

### What I learned

Creating a worktree silently strips the project's live-test credentials, because `.env.test.local` is gitignored. Every worktree-based task in this repository that touches a client package inherits that gap, and the failure surfaces late and confusingly — as a panic from inside the `genai` SDK rather than as a clear "missing configuration" message. Worth knowing before planning any future live-API work in a worktree.

The ignore list's omni entries are a standing counterexample to the tempting shortcut of verifying a model with `Models.Get`. They are the reason the lead's brief insists on a real completion, and re-reading them is what convinced me not to substitute a get-by-ID probe and call it verified.

### What was tricky

The genuinely tricky part is that the two halves of this change have very different risk profiles, and the diff hides that. The ignore entry is a pure list edit that cannot be wrong: an ignored ID is asserted about only in that it is deliberately not exported. The export is a claim about the outside world, and the whole point of the policy's alive-but-unusable rule is that such claims need evidence. A reviewer skimming a five-line diff would reasonably assume both halves are equally settled.

Deciding whether to commit the unverified export at all took some thought. I landed on committing it because the branch is local, unpushed, and reviewed before merge, so the lead can flip the disposition with one amend if verification fails — whereas handing back an empty worktree would throw away the mechanical work and the documentation sweep for no gain.

### What warrants review

The export of `ChatCompleteModelGemini3_8Flash` is unverified and is the one thing in this diff that could be wrong. Before merging, someone with `GOOGLE_KEY` must run a real completion through `ChatCompleter` on `gemini-3.8-flash` and then `GAI_MODEL_CONFORMANCE=1 go test -shuffle on -run TestModelConformance ./clients/google/`. If the completion fails the way the omni models do, the constant must be removed and `gemini-3.8-flash` moved into `ignoredModels` with the verbatim error, which inverts most of this diff.

Two coverage gaps also need a decision, both blocked on the same key. First, the thinking-level matrix in `/clients/google/chat_complete_test.go` (the `thinking level matrix` subtest) carries five rows for every exported chat model, and `gemini-3.8-flash` would be the only exported chat model with none. Filling them in requires probing which levels 3.8 accepts, so I added no rows rather than guessing. Second, the doc comments in `/clients/google/chat_complete.go` at lines 55-62 and 65-66 enumerate exactly which models accept `gai.ThinkingLevelNone` and which reject `ThinkingLevelMinimal`; `gemini-3.8-flash` belongs on one side of each list, and I could not determine which. Both were left untouched deliberately — appending 3.8 to those lists without probing would state something I do not know to be true, which is worse than an omission. The lead's brief anticipated this ("do not blindly append").

The one judgement call worth a second opinion is the reworded ignore-group comment. It now reads "Floating aliases that track the newest model, and experimental variants of those aliases", which is accurate but slightly stretches a group that was previously three clean aliases.

### Future work

Get `GOOGLE_KEY` into the worktree so the verification, the matrix rows, and the two doc-comment enumerations can all be finished; they are one live session's work once the key is available. Separately, the missing-credentials panic is an unpleasant first contact for any worktree-based task here — a skipped test with a clear message would beat a panic from inside the SDK, though that is a change to the client's test helpers and well outside the scope of #353.

## Step 3: Live-verify 3.8, land the matrix rows, and close out the gates

**Author:** flash-builder

### Prompt Context

**Verbatim prompt:** "`.env.test.local` is now in the worktree root (copied from the primary checkout; it stays gitignored). Finish in one pass: 1. Live chat completion through `ChatCompleter` with `gemini-3.8-flash`; record evidence in the diary. 2. Add the five `thinking level matrix` rows for `ChatCompleteModelGemini3_8Flash` in `clients/google/chat_complete_test.go`, probing live to get the expectations right, same as the other models. 3. Update the doc-comment enumerations at lines ~55-62 and ~65-66 of `clients/google/chat_complete.go` to place 3.8 on the correct side of each, based on what the probing shows. 4. `GAI_MODEL_CONFORMANCE=1 go test -shuffle on -run TestModelConformance ./clients/google/` green. 5. `go test -shuffle on ./clients/google/` green, `make lint` clean. Your comment widening (\"and experimental variants of those aliases\") is fine; keep it. Amend `566e47a` (still local) so the branch has one commit; add Step 3 to the diary rather than editing Step 2."
**Interpretation:** With credentials now available, do the live work Step 2 could not: prove the model, characterise its thinking-level behaviour by probing, encode that in the matrix and the doc comments, and run the gates.
**Inferred intent:** Turn the unverified export from Step 2 into a grounded one, and leave the new constant with the same depth of coverage every other exported chat model has.

### What I did

Confirmed `.env.test.local` was present and carried `GOOGLE_KEY`, then wrote a throwaway probe at `/clients/google/zzprobe_test.go` with two parts: one plain completion through `ChatCompleter` on `gemini-3.8-flash`, and a loop over all five thinking levels with repeat counts high enough to see nondeterminism.

The plain completion succeeded on the first run:

```
PROBE text="The capital of Denmark is Copenhagen." textParts=1 thoughtParts=0 usage={PromptTokens:13 ThoughtsTokens:64 CompletionTokens:7}
```

That is the evidence the policy's alive-but-unusable rule wanted: a real streamed answer with populated usage metadata, not just a successful `Models.Get`. `gemini-3.8-flash` is exportable.

Then probed the levels — 15 runs at None, 15 at Low, 20 at Medium, 20 at High, plus 3 at Minimal — all on the same prompt the matrix uses, at temperature 0. Aggregated thoughts-token counts:

| level | outcome |
| --- | --- |
| none | accepted; 0 tokens in 10 of 15 runs, otherwise 153-273 |
| minimal | rejected 3 of 3: `Error 400, Message: Thinking level MINIMAL is not supported for this model. Please retry with other thinking level., Status: INVALID_ARGUMENT` |
| low | accepted; 0 tokens in 9 of 15 runs, otherwise 151-220 |
| medium | accepted; non-zero in 20 of 20 runs, 206-306 |
| high | accepted; non-zero in 20 of 20 runs, 269-560 |

Encoded that as five rows after the 3.7 block in the `thinking level matrix` subtest of `/clients/google/chat_complete_test.go`: None and Low with no thoughts-token assertion, Minimal with `wantErr: true`, Medium and High with `wantThoughtTokens: true`. Updated both doc-comment enumerations in `/clients/google/chat_complete.go` — added `gemini-3.8-flash` to the list of models that accept `gai.ThinkingLevelNone`, and to the `ThinkingLevelMinimal` rejection list alongside `gemini-3.1-pro-preview` and `gemini-3.7-flash`. Deleted the probe file, then ran the gates.

### Why

The probe counts, not intuition, decide each row. A `wantThoughtTokens: true` row on a level that returns 0 even one run in ten is a scheduled flake, and the surrounding comments show the maintainer has already been bitten by exactly that on 3.1 Flash-Lite and Pro 3.1 ("it flaked twice in two days", "three flakes across two days"). Low was the row most at risk here: a naive reading of the level names says Low thinks, and a single lucky probe would have confirmed it. Fifteen runs showed 0 tokens in nine of them.

I probed Medium and High twenty times each rather than three because those are the two rows that do carry an assertion, so they are the two that can flake. The observed ranges (206-306 and 269-560) sit far enough from zero to be comfortable.

### What worked

The probe design paid off twice over. Running the level loop with `t.Parallel()` across levels cut the extended pass to about 30 seconds of wall time for 73 live calls, which made it cheap to probe deeply rather than settling for three runs. Reusing the matrix's own prompt and temperature meant the probe measured the same thing the permanent rows measure, so the numbers transfer directly.

Reading the existing 3.7 block before probing set the right expectation: it documents a model with exactly the two edges 3.8 turned out to have, so I knew to check both the None acceptance and the Minimal rejection specifically rather than assuming the 3.5/3.6 shape.

### What didn't work

Nothing failed in the live work itself; every probe returned what it was asked for. Two things did go sideways.

First, three subtests in the package cannot pass in this worktree. They need a Vertex AI service account via `GOOGLE_VERTEX_CREDENTIALS_PATH` and `vertex.json`; the env file carries `GOOGLE_KEY`, `GOOGLE_VERTEX_KEY`, `OPENAI_KEY`, and `ANTHROPIC_KEY` but not that path, and `vertex.json` is gitignored (`/vertex.json`) so it did not come into the worktree either. `go test -shuffle on ./clients/google/` therefore still dies:

```
--- FAIL: TestNewClient/can_create_a_new_client_with_the_Vertex_AI_backend_and_a_service_account
panic: project/location or API key must be set when using Vertex AI backend.
	/clients/google/client.go:85 (google.NewClient)
	/clients/google/client_test.go:58 (newVertexAIClientWithCredentials)
```

The three are `TestNewClient/can create a new client with the Vertex AI backend and a service account`, `TestEmbedder_Embed/can embed a text with Vertex AI backend and service account`, and `TestEmbedder_Embed/can embed a text with Embedding 2 on Vertex AI backend` (which also goes through the credentials helper despite its name not saying so), plus `TestChatCompleter_ChatComplete/can chat-complete via Vertex AI with service account`. All four sit behind `newVertexAIClientWithCredentials`, which my diff never touches, so this is the same class of environment gap as Step 2 rather than a regression. Everything else in the package passes; see below.

Second, a shell quoting trap cost a few minutes. Appending the Step 2 text with a `cat >> ... <<'EOF'` heredoc was refused outright:

```

that it stays inside the worktree. Refusing to run it
```

The diary prose mentions `git worktree add`, which is enough to trip the isolation guard on a large heredoc. Writing the file through the editing tools instead worked immediately.

### What I learned

`gemini-3.8-flash` is a 3.7-shaped model at the edges but noticeably looser in the middle. Both accept `ThinkingBudget=0` and both reject `MINIMAL`, yet 3.7 thinks anyway on roughly fifteen of sixteen None runs while 3.8 actually honours the zero budget two times in three. Anyone reading the two blocks side by side should not assume the point release inherited 3.7's behaviour wholesale — it inherited the API contract, not the disposition.

More usefully: the sample size needed to characterise one of these rows is far larger than it looks. Three probes at Low would have shown either "always thinks" or "never thinks" with about a 40% chance of each, and both readings are wrong.

The Vertex service-account path is a second, separate credential that a worktree does not inherit. `.env.test.local` alone is not sufficient to make `clients/google` green; `vertex.json` is needed too.

### What was tricky

Wording the new matrix comment honestly took two passes. My first draft said 3.8's Low was "unreliable in the same way" as 3.7's, which reads as parity and is wrong by an order of magnitude — 9 of 15 against roughly 1 in 10. I caught it in self-review and rewrote the block around what actually differs, because a comment that quietly overstates a similarity is worse than no comment: the next person to touch these rows would carry the wrong prior into their own probing.

The other subtlety is that "flash 3.8 + low" now looks inconsistent beside "flash 3.6 + low", which does assert thoughts tokens. That asymmetry is real and measured, not an oversight, which is exactly why the comment above the block carries the probe counts.

### What warrants review

The five new matrix rows are the substance. The two unasserted rows (None, Low) are deliberate and the comment gives the counts behind them; a reviewer who disagrees should re-probe rather than tighten the assertion on intuition. The Medium and High assertions rest on 20 non-zero probes each, which is fewer than the 50 the 3.7 rows cite — comfortable given the observed ranges, but that is a judgement call worth a second pair of eyes.

The doc-comment parenthetical now reads "(3.7 usually keeps thinking regardless of the zero budget, and 3.8 occasionally does)". "Occasionally" is standing in for a third of runs, which feels right in prose but is a compression of real data.

The four Vertex service-account subtests remain unrun here. If they matter before merge, `vertex.json` and `GOOGLE_VERTEX_CREDENTIALS_PATH` need to reach the worktree; nothing in this diff touches that path.

### Future work

None for #353 — the drift is resolved and the new constant has the same coverage depth as its siblings. Two standing observations carry over from Step 2: the missing-credentials panic would be friendlier as a skip with a clear message, and if Google keeps shipping Flash point releases monthly, the per-model matrix block plus two doc enumerations is a growing per-release tax that a family-level prefix rule might eventually replace.
